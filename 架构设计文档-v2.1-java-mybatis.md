## 1. 技术栈建议（Java Spring Boot 生态）
    层次	技术选型	理由
    前端	React 18 + TypeScript + Ant Design	与后端语言无关，组件生态丰富
    后端框架	Java 21 + Spring Boot 3.2	稳定、企业级生态，Spring Security 提供 RBAC + JWT 一站式支持
    持久层	MyBatis-Plus + 自定义 JSONB TypeHandler	完全控制 SQL，复杂查询和 JSONB 操作更直观，通过 TypeHandler 实现 POJO ↔ JSONB 自动映射
    数据库	PostgreSQL 15	JSONB、行级安全、审计日志只追加
    缓存	Redis 7 + Spring Data Redis	存储 JWT 黑名单、会话、K8s API 缓存（5秒）
    消息队列	RabbitMQ + Spring AMQP	异步处理审计日志、流水线任务、扩缩容事件
    K8s 交互	fabric8 Kubernetes Client (io.fabric8:kubernetes-client)	Fluent API 友好，支持动态多集群配置，与 Spring Boot 集成简单
    监控指标	Micrometer + Prometheus + metrics-server（降级）	原生 Prometheus 端点，Metrics-server 作为 fallback
    API 网关	Kong / Nginx 或 Spring Cloud Gateway	限流、认证路由，生产推荐 Kong
    认证与授权	Spring Security 6 + JJWT / Nimbus JOSE + JWT	标准 OAuth2 风格，RS256 签名
    二次验证	TOTP (Google Auth 库) + Spring Security 扩展	敏感操作二次验证
    对象存储	MinIO SDK 或 AWS S3 SDK	导出报表、审计日志归档
    异步任务	Spring @Async + ThreadPoolTaskExecutor	审计日志异步写入
    定时任务	Spring @Scheduled + Redisson 分布式锁	动态扩缩容评估（30秒）、集群健康检查，保证多实例单执行
    WebSocket	Spring WebSocket + @MessageMapping	实时日志流，对接 K8s Pod 日志
    主键策略	所有表主键使用 BIGSERIAL（自增 64 位整数），不使用 UUID。外键约束在数据库层面移除，通过应用层查询维护关联关系。

各层职责（Spring Boot 视角）：

Controller 层：接收 HTTP 请求，参数校验，调用 Service，返回统一响应（不包含业务逻辑）。

Service 层：核心业务逻辑，事务管理，权限判断（通过 Spring Security @PreAuthorize + 自定义 PermissionEvaluator）。

数据访问层：MyBatis Mapper + XML 映射文件，数据库访问。复杂 JSONB 查询使用原生 SQL + @Select 注解或 XML。

Integration 层：fabric8 Kubernetes Client、Nacos Client、Prometheus 查询器。

Async 层：@Async 处理审计日志、流水线步骤。

## 5. 与 Kubernetes 交互方案
底层为 Kubernetes，平台使用 fabric8 Kubernetes Client 与各集群 API Server 交互。

连接方式：管理服务启动时加载每个集群的加密 Kubeconfig（存储在 clusters 表），通过 KubernetesClientBuilder 动态创建 KubernetesClient 实例，并放入 Map<String, KubernetesClient> 缓存。

环境隔离：通过 K8s Namespace + 集群物理隔离实现。平台记录每个 ServiceInstance 的 namespace，操作时直接针对该 namespace 下的资源。

灰度发布：调用 Nginx Ingress Controller 的 canary annotation 调整权重。使用 fabric8 的 ExtensionsAPI 或直接 patch Ingress。

批次发布：对 Deployment 使用 maxSurge + maxUnavailable 配合自定义控制器分批；对 StatefulSet 使用 partition 参数。

实时日志：通过 fabric8 PodOperations 的 watchLog() 获取流式日志，通过 WebSocket 逐行推送前端。

预留扩展：在集群管理模块中设计接口 POST /api/v1/clusters/{id}/switch 用于未来多集群调度，并保留插件化接口。
### 5.1 JSONB TypeHandler 示例

```java
@MappedTypes({StrategyJson.class, FailureCondition.class})
public class JsonbTypeHandler<T> extends BaseTypeHandler<T> {
    private final ObjectMapper objectMapper = new ObjectMapper();
    private final Class<T> type;

    public JsonbTypeHandler(Class<T> type) { this.type = type; }

    @Override
    public void setNonNullParameter(PreparedStatement ps, int i, T parameter, JdbcType jdbcType) throws SQLException {
        ps.setObject(i, objectMapper.writeValueAsString(parameter), java.sql.Types.OTHER);
    }

    @Override
    public T getNullableResult(ResultSet rs, String columnName) throws SQLException {
        return objectMapper.readValue(rs.getString(columnName), type);
    }
    // ... 其他方法
}
```

### 5.3 优势
完全控制 SQL，便于优化复杂的 JSONB 查询（如 ->>、@>、? 操作符）。

## 6. 安全设计（Spring Security 实现）
认证：JWT（RS256），有效期 8 小时，支持 Refresh Token。

Spring Security 配置 JwtAuthenticationFilter，验证 Authorization 头。

登录成功后使用 JJWT 生成令牌，私钥存储在 K8s Secret。

权限中间件：基于 RBAC + 环境级。

自定义 @PreAuthorize("hasPermission(#serviceId, 'SCALE')")，通过实现 PermissionEvaluator 查询 user_roles 表判断用户是否有权操作目标服务所在部门的环境。

敏感操作二次验证：使用 TOTP，要求请求头 X-TOTP-Code。

实现一个 TOTPFilter，在需要二次验证的接口（如发布、扩缩容）上校验。

API 限流：使用 Bucket4j 或 Resilience4j 配合网关层实现，默认 100 次/分钟，敏感操作 20 次/分钟。

审计日志防篡改：audit_logs 表只追加（数据库层面禁用 UPDATE），应用层通过 @Async 将日志发送到 RabbitMQ，消费者批量插入。每行存储前一行的 SHA256 哈希。

数据加密：Kubeconfig 使用 AES-256-GCM 加密，密钥从 Spring Boot 的 application-secret.yml 或 Vault 读取。

## 7. 关键流程时序说明（灰度发布）
text
用户(运维) → 前端 → API网关 → Spring Boot Controller → Service → K8s/Nginx/Nacos → DB

1. [创建灰度任务]
   用户 POST /api/v1/canary/tasks
   → Controller 校验权限（生产环境需审批权）
   → Service 创建 DeploymentTask 记录，状态=internal_test
   → 调用 fabric8 创建金丝雀 Deployment（副本数1，无流量），并注册到 Nacos 但权重0
   → 生成内部测试访问链接（管理服务代理路由）
   → 返回任务ID

2. [内部测试阶段]
   用户 GET /canary/tasks/{id}/internal-endpoint 获取链接
   → 访问代理（Spring Boot 内置代理或网关路由）-> 转发至金丝雀 Pod（JWT 认证）
   → 验证完成后点击“请求接入流量”

3. [请求接入流量 - 审批]
   用户 POST /canary/tasks/{id}/stage/request_traffic
   → 若策略 auto_approve_traffic=false
        → Service 创建审批单（关联 deployment_tasks），通知部门主管（异步消息）
   → 部门主管 POST /approvals/{id} (action=approve)
        → 审批通过，Service 将任务推进到小流量阶段
        → 调用 fabric8 修改 Nginx Ingress canary-weight=5

4. [小流量验证]
   → 后台 Scheduled 任务（每30秒）查询 Prometheus：
       金丝雀版本请求量 ≥ 10 QPS 且 错误率 > 5% 持续 2 分钟 → 设置任务 status=paused 并告警

5. [扩大流量]
   用户手动 POST /canary/tasks/{id}/stage/promote_25
   → Service 修改 canary-weight=25，继续监控
   → 同样支持 promote_100

6. [全量与清理]
   promote_100 后，Service 将稳定版 Deployment 更新为新镜像，删除金丝雀 Deployment
   → 任务状态=success

## 8. 动态扩缩容算法（Java 伪代码）

```java
@Scheduled(fixedDelay = 30000)
@RedissonLock(key = "autoscaling-lock", waitTime = 0)
public void evaluateAutoScaling() {
    List<AutoScalingPolicy> policies = policyRepository.findEnabled();
    for (AutoScalingPolicy policy : policies) {
        double currentValue = fetchMetric(policy);
        int currentReplicas = getCurrentReplicas(policy.getServiceInstanceId());
        int targetThreshold = policy.getTargetThreshold();
        int min = policy.getMinReplicas();
        int max = policy.getMaxReplicas();
        long cooldown = policy.getCooldownSeconds();

        if (currentValue > targetThreshold && consecutiveExceed >= 3) {
            int desired = (int) Math.ceil(currentReplicas * (currentValue / targetThreshold));
            desired = Math.min(max, Math.max(min, desired));
            if (desired != currentReplicas && (now - lastScaleTime > cooldown)) {
                scaleTo(policy.getServiceInstanceId(), desired);
                lastScaleTime = now;
            }
        } else if (currentValue < targetThreshold * 0.8 && lowLoadMinutes >= scaleDownDelay) {
            int desired = (int) Math.ceil(currentReplicas * (currentValue / targetThreshold));
            desired = Math.min(max, Math.max(min, desired));
            if (desired < currentReplicas && (now - lastScaleTime > cooldown)) {
                scaleTo(policy.getServiceInstanceId(), desired);
                lastScaleTime = now;
            }
        }
    }
}
```

## 9. Nacos 集成设计（Java 实现）
服务健康状态：使用 NacosClient（com.alibaba.nacos.client.naming.NacosNamingService），每 30 秒拉取服务实例列表，匹配 K8s Pod IP，更新到数据库 nacos_health_status 字段。

QPS 指标：若用户选择基于 Nacos 的 QPS 指标，则调用 Nacos OpenAPI /nacos/v1/ns/instance/list 或统计端点获取请求量数据（需 Nacos 开启监控）。也可由 Prometheus 抓取 Nacos 暴露的 metrics。

降级策略：Nacos 不可用时（连接失败、超时），服务列表中的 Nacos 状态显示“未知”，扩缩容策略若依赖 QPS 则标记为 error，并降级到 CPU 或 memory 指标（若策略有配置 fallback）。

## 10. 集群健康检查与高可用（Spring 实现）
健康检查：Spring @Scheduled(fixedDelay = 30000)，每个集群独立执行，调用 fabric8 KubernetesClient.version()，连续 3 次失败则更新 clusters.status='offline'。

分布式锁：使用 Redisson RLock 确保动态扩缩容、定时报表生成等任务只在一个实例上执行。

无状态设计：所有会话、JWT 黑名单、缓存存储在 Redis；使用 @EnableRedisHttpSession 或手动存 token。

## 11. 架构风险提示（不变）
风险	缓解措施
Nacos 集成复杂度及稳定性	仅做只读操作，使用熔断器（Resilience4j 或 Spring Cloud Circuit Breaker），降级显示未知
灰度自动暂停依赖 Prometheus 查询	Prometheus 查询超时（5 秒）则跳过该次检查，保留上次状态，告警通知运维
批次发布 StatefulSet partition 模式需用户明确	API 中提供 statefulset_partition_mode 字段，前端强提醒
管理服务与集群网络不稳定	健康检查 + 断路器，失联集群返回 503，记录审计日志
